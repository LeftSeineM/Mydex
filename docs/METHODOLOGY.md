# Mydex 方法论：如何把微信本地会话接入 AI

版本：0.1.0 · 2026-10-21

本文依据整理时读到的源码解释实现。源码中的检查机制属于已核查事实；真实环境可用性仍受客户端版本、登录状态、账号授权和依赖影响。本次没有重新进行微信实发实验。

## 一、连接的对象是什么

Mydex 连接用户自己电脑上已经登录的微信桌面客户端。账号登录仍由微信完成。项目把客户端进程、进程创建时间、可执行文件位置、模块哈希、当前账号和允许的会话组合成一次绑定，不能只凭一个可能被复用的 PID 继续工作。

相关代码：`deployment/enroll_local.py`、`app/account_scope.py`、`app/native_sender_bridge.py`。

“连接到进程”有两个不同用途：读取侧核查进程并定位文件/必要内存信息；发送侧使用与特定微信构建匹配的原生组件。不能把两者统称为一个普通 HTTP 接口，也不能宣称使用官方 Bot API。

## 二、怎样定位和读取本地聊天文件

1. **定位当前账号文件。** `inspect_open_databases.py` 检查目标进程已经打开的磁盘文件句柄，筛选当前使用的数据库路径。这样不用把某个用户目录写死为唯一来源。
2. **验证解密条件。** 聊天库不是可直接读取的普通明文文件。账号录入流程检查客户端版本，并验证候选密钥是否能通过真实数据库页的认证。未经认证的数据不能作为聊天记录输入。
3. **建立只读数据库视图。** `history_crypto.py` 执行页认证和解密；`history_vfs.py` 在内存中提供 SQLite 可读视图，并合并已提交的 WAL 日志帧。源数据库变化会使快照失效并触发受控重试，避免混合不同事务。
4. **按会话读取并标准化。** `history_reader.py`、`session_history.py` 解析发送人、时间、消息类型和正文；压缩正文有大小限制。缺失或不支持的图片、语音、附件正文不冒充已读。
5. **保存必要索引。** 原库只读、解密页留在内存，不代表程序完全不落地聊天信息：应用自己的本地索引和会话状态可能保存选中消息及生成内容，必须作为私人数据管理，排除 Git。

DPAPI 保护的本地密钥与 Windows 用户绑定。复制一个密钥文件到另一台电脑，并不等于可以直接解密或接管原账号。

## 三、从记录到“可用记忆”

`history_context.py` 先限定会话，再识别时间范围、话题和统计需求，从本地已获取记录中选取依据。涉及计数或排名时由程序计算，模型得到的是有限证据和上下文。`lab.py` 的 `Engine.summarize_history()` 提供手动总结入口，`server.py` 将它暴露为本机控制台的 `/api/history/summary`。

推荐总结结构：本期讨论、已决定事项、待办与责任人、未解决问题、证据时间范围。没有明确责任人或截止时间就写“待确认”；不能替参与者补造承诺。

摘要必须标明“依据本地已获取记录”。本地未同步的历史、未取得的数据库分片或附件正文不属于模型证据。

## 四、从新消息到 AI 回复

`database_inbox.py` 和 `account_assistant.py` 读取新事件，过滤历史回放、自身消息和不在许可范围的会话。真实 @ 和指定联系人私聊走各自规则，可选群聊参与还受节流策略控制。

`conversation_queue.py` 维护每个会话的工作状态，保证同一会话按序处理；不同会话共享受限并发。`group_scopes.py` 和 `account_scope.py` 限定对象，`lab.py` 组织模型请求。群 A 的记录不能作为群 B 或某个私聊的默认上下文。

用户选择远程模型时，选中正文会跨出本机发送给该服务。产品界面应让管理员知道使用了哪个服务、哪些会话被授权，不应把“本地读取”宣传成“从不上传”。

## 五、回复怎样回到微信

`native_sender_bridge.py` 将有来源关联的回复草稿交给原生发送通道。`app/research/worker_sender_v6/` 保存当前发送组件的 C 源码和 Python 控制层；MinHook 是底层依赖之一。

实现依赖已验证客户端的内部调用约定、结构和线程环境。发送任务先排队，再由匹配的客户端工作线程执行；不是任意线程上随意调用内部函数。客户端文件哈希、原生构件证明、账号和会话绑定都要通过检查。

“函数返回成功”与“用户收到消息”不是同一个结论。当前实现会核对认证过的出站记录；发送结果不明确时保留待核查状态，不盲目重试。`send_guard.py` 负责发送配额、暂停与相关保护。客户端重启会使旧绑定失效，需要重新录入验证。

## 六、定期整理如何接在这条链路上

已有链路解决了读取、检索和生成摘要。要做稳定日报/周报，还需要一层调度：会话、时间窗、时区、执行时间、投递位置和授权范围；用“会话 + 时间窗 + 报告类型”作为去重标识，保存上次完成位置。

调度到点后执行“取授权时间段记录 → 生成摘要 → 保存本地报告”；仅在明确开启投递时，再进入现有发送保护链。失败应记录原因并有限重试，机器离线后不能补发一长串旧报告。

**这段是扩展设计，不是本版本已经验收的通用定期报告功能。** 本次查到的历史定时消息脚本不能证明具备任意会话、任意周期的日报系统，因此没有把这些一次性脚本打包为正式入口。

## 七、迁移时保留哪些不变量

- 当前账号与当前进程必须重新核实，禁止套用旧会话证明。
- 版本/哈希不匹配就停止，禁止绕过检查。
- 同一账号保持单一发送执行者，避免双机重复回复。
- 历史导入不触发回复，重启不重放旧任务，未知发送结果不自动重试。
- 配置、密钥、聊天索引、日志与源码分开保存。

这套方法的价值是把客户端适配、历史证据、模型生成和发送确认分成可检查的环节；任何一环失败，都能指出停在哪里，而不是把所有问题都归给模型。
